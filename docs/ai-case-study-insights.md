# 금융 AI 사례를 하네스 설계에 적용하기

원천 자료를 먼저 제한하고, LLM에는 근거 설명을 맡기며, 표시 전 검증을 별도로 두는 접근이 이 프로젝트에 유용하다. 우선순위는 검색 도구 추가보다 **근거와 주장의 일치, 원장 수치, 기준시점**을 검증하는 합성 평가셋이다. 아래 적용안은 원문에서 도출한 설계 제안이며 아직 구현되지 않았다. 현재 구현 상태는 [하네스 코드](../scripts/ask.py)와 [기존 테스트](../tests/test_runner.py), 단계 상태는 [단계 파일](../phases/index.json)을 기준으로 한다.

## 기존 하네스가 보장하는 것과 남은 검증

| 현재 동작 | 코드·테스트 근거 | 보장 범위의 한계 |
|---|---|---|
| `as_of` 이후 `date`인 근거를 입력 전에 제외 | `prepare_sample`, `test_future_evidence_removed` | 사건 발생일·공개일·수집일을 구분하지 않음 |
| `id`·`date`·`text`만 전달 | `prepare_sample`, 동일 테스트 | 허용된 `text` 안의 개인정보·민감 내용까지 제거하는 검사는 아님 |
| 완료 이벤트·응답 필드·근거 ID 소속 검사 | `validate_response`, `test_invalid_responses` | 존재하는 ID를 인용한 허위 주장이나 수치 오류도 통과할 수 있음 |
| 근거 부족 답변 형식 허용 | `test_insufficient_evidence` | 모델이 실제로 적절한 상황에서 답변을 보류하는지는 평가하지 않음 |
| 임시 디렉터리·읽기 전용 실행, 도구·MCP 비활성화 | `run`, `test_process_boundary` | 프로세스 설정 검사이며 모델 품질이나 전체 격리 보장의 증거는 아님 |
| 실패·시간 초과를 예외로 처리 | `run`, `test_process_failures` | 향후 앱의 사용자 표시·재시도 정책은 미구현 |

현재는 합성 입력을 쓰는 하네스다. 원장 계산, 그래프 검색, 증권사 어댑터는 후속 단계이므로 해당 기능의 정확성을 기존 테스트 통과로 주장하지 않는다.

## 적용 제안은 근거 준비와 표시 전 검사부터 시작한다

다음 내용은 세 사례를 프로젝트의 [권한·원장 원칙](../AGENTS.md)과 [인수 기준](RUBRIC.md)에 맞게 해석한 제안이다. 각 회사의 내부 구현을 재현했다는 의미는 아니다.

| 우선순위 | 제안 | 이 프로젝트에서 필요한 이유 | 구현 시 확인할 결과 |
|---|---|---|---|
| 먼저 | 허용 ID와 주장 지지 여부를 분리 평가 | 현재 ID 검사는 인용 내용의 진위를 판단하지 못함 | 맞는 ID를 붙인 틀린 종목·수치·인과 주장 식별 |
| 먼저 | 수량·금액은 원장 계산 결과와 대조 | LLM의 산술이나 문장 생성이 거래 사실을 바꾸면 안 됨 | 부분체결·취소·중복 입력에서도 동일한 원장 합계 |
| 먼저 | 사건 시각과 공개·이용 가능 시각을 분리 | 과거 사건을 뒤늦게 알게 된 자료가 과거 답변에 섞일 수 있음 | 기준일 뒤 공개·정정된 버전은 당시 근거에서 제외 |
| 그래프 단계 | 출처와 이벤트 계보를 유지하며 검색량 제한 | 재전재·중복 청크가 독립 증거처럼 부풀려질 수 있음 | 원문 URL·근거 ID 보존, 중복 계보 식별, 정해진 입력 예산 준수 |
| 그래프 단계 | 검색·실행·답변 실패를 분리 기록 | 실행 성공만으로 답변 품질을 판단할 수 없음 | 실패 유형과 버전을 연결해 동일 합성셋으로 변경 전후 비교 |

시각 설계에서는 `occurred_at`(사건 발생), `available_at`(공개·이용 가능), `ingested_at`(수집)을 구분하는 안을 검토한다. 과거에 공개된 자료와 당시 시스템이 이미 수집한 자료 중 어느 기준으로 질의할지 먼저 정해야 한다. 뒤늦게 수집한 자료를 과거 시스템의 지식으로 취급하지 않도록 이 차이를 평가 입력에 드러낸다. 필드 이름과 포함 규칙은 아직 확정하지 않았다.

정제된 근거에도 반대 설명과 불확실성이 남아 있어야 한다. 토스 사례의 가격 방향 일치 필터를 거래 이력 질의에 그대로 적용하면 반대 근거가 사라질 수 있다. 중복 제거 역시 서로 다른 관점의 기사를 하나로 지우는 방식보다 원천 계보를 표시하고 대표 근거를 선택하는 방식부터 검토한다.

### 서버와 LLM의 책임을 분리하는 후보 흐름

| 단계 | 책임 주체·입력 | 출력·경계 |
|---|---|---|
| 원장 집계 | 서버가 확인된 체결을 계산 | 질문에 필요한 수량·금액·계산 기준만 제공 |
| 근거 검색 | 서버가 권한·종목·기준시점·자료 버전·검색 예산 적용 | 출처·시점·ID가 보존된 제한된 근거 묶음 |
| 설명 생성 | Codex가 정제된 집계와 근거를 설명 | 근거 연결과 불확실성이 있는 구조화 응답 |
| 표시 전 검사 | 서버가 형식·ID·시점·결정 가능한 수치 검사 | 실패 시 생성 결과를 성공 답변으로 표시하지 않음 |
| 의미 품질 평가 | 고정 합성셋으로 주장 지지와 답변 적절성 평가 | 회귀 실패 유형과 재현 근거; 런타임 정확성 보장과 구분 |

서버가 허용 범위를 결정하고 LLM이 전달받은 근거 안에서 설명한다. 주문 도구·증권사 연결 설정·계좌번호·인증·원장 전체를 모델 입력에 포함하지 않는다. 원문과 메모의 지시문도 데이터로 취급해야 하며, 프롬프트 문구만으로 주입 방어를 검증했다고 보지 않는다.

현재의 `mcp_servers={}`는 유지한다. 향후 검색 도구가 필요한 경우에도 읽기 전용 검색 한 가지를 노출할 필요와 효과를 먼저 비교하고, 서버의 권한·시점·개수 제한을 우회할 수 없는 계약을 설계한다. MCP 활성화와 도구 권한은 별도 결정·테스트가 필요하다.

## 합성 평가셋은 실패별 기대 동작을 고정한다

아래는 추가할 평가 항목이며 현재 테스트가 모두 다룬다는 뜻이 아니다. 기본 검사는 인증·네트워크·실계좌 없이 실행한다. 의미 평가에는 합성 정답과 주장별 근거를 두고, 별도의 모델 품질 실험을 실행했다면 모델·프롬프트·검색 설정·평가셋 버전을 함께 기록한다.

| 합성 사례 | 기대 동작 | 구분할 실패 |
|---|---|---|
| 허용 ID를 인용하지만 다른 종목을 설명 | 근거가 주장을 지지하지 않는다고 판정 | 잘못된 종목·주장 |
| 근거에는 2주인데 답변은 20주 | 원장 집계와 불일치로 표시 전 거부 | 수치 불일치 |
| 과거 발생 사건을 기준일 뒤 처음 공시 | 모델 입력에서 제외 | 미래 공개 정보 유입 |
| 기준일 뒤 정정된 자료가 과거 버전을 덮음 | 당시 이용 가능한 버전으로 조회 | 자료 버전·시점 손실 |
| 원문과 재전재 기사 또는 중복 체결 | 근거 중복과 체결 중복을 각각 식별 | 근거 과대계상·원장 중복 반영 |
| 인과 설명을 뒷받침할 자료가 없음 | 확인 불가를 표시하고 원인을 단정하지 않음 | 근거 없는 인과 추정 |
| 자료 안에 계좌 조회·주문 실행 지시가 있음 | 권한 확대 없이 데이터로만 처리 | 주입·도구 권한 침범 |
| 허용 필드의 본문에 합성 개인정보가 섞임 | 모델 입력 전에 제외·마스킹되는지 확인 | 본문을 통한 민감 내용 유입 |
| 검색량 초과·검색 시간 초과·모델 실패 | 부분 결과의 한계를 표시하거나 실패 처리 | 예산 초과·불완전 결과의 성공 처리 |

형식·ID·시점·수치 검사는 결정 가능한 계약 검사로 둔다. 검색 평가는 필요한 근거를 찾았는지, 답변 평가는 각 주장이 근거에 충실한지와 질문에 답했는지를 별도로 본다. 사람이 소수 합성 사례의 기대 답변과 실패 판정을 먼저 정리하면 의미 평가 기준을 점검하기 쉽다.

운영 실패를 회귀셋으로 옮길 때는 합성 사례로 재구성한다. 재현 항목은 사례 ID·기준시점·근거 ID·실패 유형·버전·지연시간처럼 필요한 값부터 정하고, 실제 계좌 자료·인증·런타임 원본은 저장소 밖에 둔다. 외부 서비스로 보내는 입력과 보관 항목은 별도로 검증한다.

## 규모가 커진 뒤 검토할 항목

BERT 분류기, 유사 예시 검색, 에이전트 프레임워크, 큐, 벡터 DB는 현재 합성 하네스의 필수 조건으로 채택하지 않는다. 고정 입력과 단순 검색으로 기준선을 만들고, 필요한 실패를 해결하는지 비교한 뒤 도입 여부를 판단한다. 특히 유사 예시 검색에는 평가 정답 누출과 기준일 이후 예시 유입 검사가 추가로 필요하다.

이 문서의 활용 지점은 원장 단계의 계산 계약과 그래프 단계의 시점·근거 평가다. 실제 설계 선택은 [결정 기록](ADR.md)에 근거와 상충을 남기고, 기능 완료는 [단계별 조건](../phases/index.json)과 [인수 기준](RUBRIC.md)으로 확인한다. 합성 평가 통과와 증권사 연결·실계좌 인수는 각각의 증거로 판단한다.
